# Durable delivery and recovery

Status: accepted on 26 November 2026. Use Vercel Workflow SDK (`workflow` and `@workflow/nest`) with managed Vercel execution/queues and Expo push. There is no notification polling, always-on worker, Redis service, or websocket channel. This protocol is a design to implement and prove in staging, not a claim that jobs already run.

## Durable command boundary

A business transaction followed by untracked sending can lose every push if the function dies after commit. Route notification-producing changes through a durable operation before changing session state:

1. Authenticate/validate the request and its per-user idempotency key. Store a `CommandOperation` containing actor, expected aggregate version, request digest, encrypted input, creation/expiry times, and operation ID. This preparation has no business effect. Same key with different input returns `409 IDEMPOTENCY_CONFLICT`.
2. Start a durable workflow with only the operation ID. Await accepted run creation before acknowledging acceptance. A crash before start leaves only an unaccepted prepared command; retrying the same key starts it safely. Duplicate workflow starts are harmless because execution is database-idempotent. No periodic scan dispatches prepared commands.
3. In a workflow step, lock the command, recheck current actor/account/session authorization and the 24-hour command deadline, then lock the target session before memberships. Apply business changes, aggregate version, recipient notifications, delivery events and safe command result in one transaction. Already committed operations return their stored result before any deadline check, without duplicating effects. Invalid/stale/expired commands record a terminal rejection without mutation. Erase private command input at commit/rejection.
4. Later durable steps dispatch stored safe projections and schedule any completion-generation lifecycle work. A crash after commit resumes dispatch; repeated steps deduplicate notification IDs and tolerate duplicate external delivery. Store only IDs, counts and redacted outcomes in workflow arguments/returns: never exact addresses, tokens, codes, or command bodies.
5. The request waits at most ten seconds for the committed result. Return normal `200`/`201` or a domain error when available, otherwise `202` with operation ID and pending state. `202` never means a seat was confirmed. Complete UI state through the command result/push, or one explicit recovery read on entry/re-entry or user action; never poll an operation endpoint. Caller session revocation prevents exposing a result even if the command already committed.

Use this for publishing, edits, participation transitions, cancellation, and notification-producing moderation/cleanup. Auth exchange, logout and immediate security disable are synchronous security operations, not delayed notification commands. Account deletion synchronously disables the account/revokes sessions and writes its deletion ledger before acknowledging success; durable cancellation/purge then uses an idempotent deletion job authorized by that recorded deletion request. A security revocation cannot wait for push delivery. Associated security-notification handoff is best effort after the disable, while the security action itself stays committed; there is no promise of a security push after a crash in that handoff. Read-only routes do not need notification workflows. Bound fan-out to active requests/participants and reuse operation IDs throughout. If workflow start fails, expose retryable unavailability without a business commit. If execution permanently fails after a commit, preserve authoritative inbox/state and record a redacted failure for operator-triggered replay by event ID. No silent rollback of an accepted seat and no automated notification-table scans.

The [official NestJS integration](https://workflow-sdk.dev/docs/getting-started/nestjs) is currently beta. Use its SWC integration and Vercel build-output command so the generated queue consumer is deployed alongside NestJS. Steps do not inherit Nest dependency injection: initialize a bounded adapter inside the step and call shared business logic. Verify crash recovery on the actual pinned versions, not only a mocked workflow. See [Workflow limits](https://vercel.com/docs/workflows/pricing) and [run access](https://workflow-sdk.dev/docs/api-reference/workflow-api/get-run).

## Notification contract

- Events cover requests, decisions, withdrawals, cancellation, material edits, completion, moderation, and account/security changes. Increment session version for every session/participation state change. Use a separate monotonically increasing recipient inbox revision, so account/security notifications do not require a game session ID.
- Initial snapshot includes personal-session state, inbox and version markers. Each recipient's push carries event/notification/operation IDs, aggregate ID/version, and a complete small safe projection: status, counts, time, format, city and their own membership/host participation state. Approval is never inferred solely from untrusted push data to grant map access.
- No exact address/coordinates, venue name, credentials, or long user content in push text/data. Keep the full serialized push under 4 KiB. Mark other cached descriptive fields as changed without fetching automatically; load them on explicit detail navigation/refresh. Never truncate a projection into an unsafe partial patch.
- Deduplicate event IDs and ignore older aggregate projections. Delayed distinct inbox entries can still be inserted without overwriting newer session state. Track inbox revision gaps and mark reconciliation needed; do not fetch on every event. Mutation results apply the same version rules.
- Revoke/clear exact-location caches on withdrawal, cancellation, completion, moderation, session relocation, logout and deletion. Keep precise map data in memory only. Check server time/authorization on each protected location read; deny at end/cancel time even if the completion job is late.
- Read the snapshot once on authenticated entry or foreground re-entry, plus explicit refresh. No client timers, background fetch job, or periodic inbox/database polling. APNs/FCM/Expo delivery is best effort; background/killed apps may not execute a listener. Explicitly opened uncached details still use protected API requests.

## Bounded push execution

Use `expo-server-sdk`, server-held push access credentials and per-environment device associations. Batch Expo sends within provider limits. Attempt an event at most five times across a 24-hour deadline, retrying transient failures with jitter around one, five, fifteen and sixty minutes, respecting `Retry-After`; do not retry permanent errors. A workflow sleep schedules one receipt check around 15 minutes after ticket issuance and at most one further check for pending receipts. Disable `DeviceNotRegistered` tokens. Unknown terminal delivery is recorded for support while the inbox remains authoritative. Receipt checks address known tickets only, never scan the notification table. See [Expo sending and receipts](https://docs.expo.dev/push-notifications/sending-notifications/).

Push is enabled by default only after OS permission; allow users to turn it off in settings. In-app transactional notifications remain available. An installation belongs to at most one currently signed-in user; remove/rebind association atomically on logout/account switch. Denied permission never blocks session use.

## Scheduled lifecycle and maintenance

Publishing or editing the end time schedules a durable completion workflow keyed by session ID, completionGeneration and expected end. Increment this generation only for end/lifecycle changes, not ordinary aggregate-version changes. Old jobs recheck current generation/end and exit if obsolete; exact authorization and join cutoffs use current server time rather than trusting scheduler punctuality. Session edits run only while draft/published; cancelled/completed sessions are terminal historical records, with duplication into a new draft available for a new game. Hosts retain all business-field edits, including participation, in active sessions under capacity/time invariants.

Use a protected daily Vercel cron invocation at 03:00 UTC to start idempotent retention/expiry batches, with durable continuation for bounded remaining work. This is housekeeping, not notification polling. Maintenance also resumes recorded account-deletion requests if their initial job handoff failed, so synchronous security disable cannot strand deletion beyond its deadline. This scan concerns deletion/retention work, never notification dispatch. Scope staging to its own resources. Retention periods and recovery limits are defined in [Operating policy](./operational-proposal.md).

## Acceptance evidence

Before pilot: prove restart before/after durable acceptance, commit-before-dispatch crash, duplicate workflow start, expired command, stale actor authorization, terminal rejection, receipt retries, out-of-order pushes, session time edits, quotas and deployment consumer operation. Assert no business effect before durable acceptance, one capacity effect per command, inbox survival after push failure, no precise data in workflow history, and no timed/per-push reads. Operator repair explicitly targets an event/operation ID. Infrastructure failure blocks launch until resolved within zero budget; it is an implementation acceptance gate rather than another open product choice.
